## 25. Database Indexing

### What
A specialized data structure (most commonly B-Trees, B+ Trees, Hash maps, or Inverted Indexes) created alongside database tables that holds references to specific table rows, enabling rapid row lookup without scanning the entire disk table (Full Table Scan).

### Why
- Turns full table scans of complexity $O(N)$ into logarithmic search $O(\log N)$ or constant time $O(1)$.
- Drastically reduces disk I/O, CPU consumption, and query latency on high-volume tables.

### Where We Use Them
- Primary and Foreign keys, columns frequently queried in `WHERE`, `JOIN`, `ORDER BY`, and `GROUP BY` clauses.
- **B-Tree**: Default in PostgreSQL/MySQL for range and equality lookups.
- **GIN/GiST**: PostgreSQL full-text search and geospatial coordinates.
- **Inverted Index**: ElasticSearch, Apache Lucene.

## 26. Query Optimization

### What
The process of analyzing, refining, and restructuring SQL queries, indexes, and execution plans generated by the database query optimizer (RBO/CBO) to execute in the least amount of time and hardware resources.

### Why
- Inefficient queries lock tables, deplete database connection pools, waste RAM on disk-to-memory sorting, and throttle entire applications.
- Small indexing adjustments or query rewrites can yield 100x to 1000x latency improvements.

### Where We Use Them
- Running `EXPLAIN ANALYZE` (PostgreSQL) or `EXPLAIN` (MySQL) to inspect sequential scans, nested loops, and memory sorts.
- Eliminating wildcard `SELECT *`, utilizing covering indexes, avoiding function calls on indexed columns in `WHERE` clauses (e.g., `WHERE DATE(created_at) = ...`), and converting subqueries to explicit `JOIN`s.

## 27. N+1 Queries

### What
A performance anti-pattern common in Object-Relational Mappers (ORMs) where fetching a parent list of $N$ records causes the application to issue 1 initial query to fetch the parent rows, followed by $N$ separate subsequent queries to fetch related child entities.

### Why
- An operation fetching 1,000 blog posts issues 1,001 database queries over the network instead of 1 or 2 batch queries.
- Severely exhausts database connection pools, multiplies network roundtrips, and spikes database CPU.

### Where We Use Them
- Detected via APM tools (Datadog, New Relic) or query log monitors.
- Resolved via **Eager Loading**:
  - Hibernate/JPA: `JOIN FETCH` or `@EntityGraph`.
  - Prisma: `include: { author: true }`.
  - Django ORM: `select_related()` (for foreign keys) and `prefetch_related()` (for many-to-many).
  - Rails ActiveRecord: `includes(:author)`.

## 28. Connection Pooling

### What
A cache of pre-established, persistent database connections maintained in memory by an application or proxy server, allowing client threads to borrow an active connection, execute a query, and return it to the pool instead of creating and destroying connections per request.

### Why
- Establishing a new database connection involves expensive TCP handshakes, TLS negotiation, authentication, and backend process spawning (especially in PostgreSQL where each connection spawns a new OS process).
- Prevents database crashing from out-of-memory errors caused by thousands of concurrent application connections.

### Where We Use Them
- Application-level pools: HikariCP (Java/Spring Boot), pgxpool (Go), SQLAlchemy (Python).
- Server-level proxies: PgBouncer, AWS RDS Proxy (vital for serverless AWS Lambda workloads connecting to relational DBs).

## 29. Read Replicas

### What
Secondary database instances that maintain a synchronized, read-only copy of the primary database by continuously consuming and applying replication logs (WAL / binlog) emitted by the primary.

### Why
- Read operations typically outweigh writes in web applications by 10:1 or 100:1.
- Offloads heavy read traffic, reporting, and search queries from the primary node, preserving primary CPU exclusively for writes.

### Where We Use Them
- Cloud databases (AWS RDS Aurora Read Replicas, Google Cloud SQL replicas).
- Application database routers directing `SELECT` queries to replica pools and `INSERT/UPDATE/DELETE` queries to the primary.

## 30. Sharding

### What
A horizontal scaling technique that splits a massive database into smaller, independent physical database instances (shards), where each shard contains a distinct subset of rows determined by a shard key (e.g., `user_id % num_shards` or consistent hashing).

### Why
- Relational databases eventually hit physical limits of vertical scaling (RAM, disk I/O, storage capacity on a single machine).
- Distributes read/write throughput and storage across dozens or hundreds of commodity servers.

### Where We Use Them
- Large multi-tenant platforms (Slack, Discord, Twitter/X) sharding user data by `tenant_id` or `guild_id`.
- Native sharding engines: MongoDB, Vitess (MySQL sharding for YouTube), Citus (PostgreSQL).

## 31. Partitioning

### What
Dividing a single large database table into smaller, distinct logical subsets within the *same* database instance based on defined rules (Range, List, Hash, or Composite partitioning) while remaining queryable through the parent table name.

### Why
- **Partition Pruning**: The query planner scans only the specific partition containing the requested data range, ignoring billions of other rows.
- **Fast Purging**: Dropping an old partition (e.g., dropping month-old logs with `DROP TABLE logs_2026_01`) is an instantaneous $O(1)$ DDL operation compared to a catastrophic `DELETE FROM logs WHERE date < ...` that causes table locks and massive WAL bloat.

### Where We Use Them
- Time-series data, financial transaction logs, audit trails (PostgreSQL Declarative Partitioning, MySQL Table Partitioning, ClickHouse, Apache Cassandra).

---

## 32. Replication

### What
The continuous copying and synchronization of database state, transactions, and binary logs from a primary node to one or more secondary replica nodes across local racks or geographic regions.

### Why
- **High Availability**: Provides immediate failover targets if the primary hardware node dies.
- **Data Durability**: Protects against catastrophic data loss.
- **Geographic Proximity**: Serves read traffic closer to regional users.

### Where We Use Them
- **Synchronous Replication**: Primary waits for at least one replica to commit before acknowledging the client (strong consistency, higher write latency).
- **Asynchronous Replication**: Primary writes locally and confirms immediately; replicas catch up asynchronously (low write latency, risk of replication lag and minor data loss during failover).
- MySQL Binlog replication, PostgreSQL WAL streaming, MongoDB replica sets.

---

## 33. Leader Election

### What
A consensus mechanism in distributed clusters where a group of peer nodes dynamically elect one node as the central coordinator (leader/primary) responsible for sequencing writes, managing state changes, and driving consensus.

### Why
- Prevents **split-brain** and ensures single-writer ordering across a cluster of independent nodes.
- Automatically selects a new leader when the current leader crashes or is partitioned, maintaining system availability without manual intervention.

### Where We Use Them
- Consensus protocols: Raft (etcd, HashiCorp Consul), Paxos (Google Chubby, Spanner), ZAB (Apache ZooKeeper).
- Kafka controller election, Kubernetes control plane (`kube-scheduler`, `kube-controller-manager` leader leases).

## 34. CAP Theorem

### What
A foundational distributed computing theorem (Brewer's Theorem) stating that in the presence of a network partition (**P**), a distributed data store can guarantee at most one of two properties:
- **Consistency (C)**: Every read receives the most recent write or an error.
- **Availability (A)**: Every non-failing node returns a successful response (without guaranteeing it is the most recent write).

### Why
- In real-world physical networks, network partitions (**P**) are unavoidable.
- Forces system designers to make an intentional tradeoff: prioritize strict correctness (CP) or uninterrupted uptime (AP) during network failures.

### Where We Use Them
- **CP Systems**: Traditional banking, financial ledgers, distributed locks (etcd, Consul, ZooKeeper, CockroachDB).
- **AP Systems**: Social media timelines, shopping carts, DNS, Cassandra, DynamoDB (with eventual consistency mode).

---

## 35. Eventual Consistency

### What
A weak consistency model in distributed data stores guaranteeing that, given no new updates occur, all replicas across the system will eventually converge and return identical values when queried.

### Why
- Enables ultra-low write latencies and high availability across globally distributed datacenters by avoiding synchronous multi-region locking.
- Ideal for use cases where reading slightly stale data for a few hundred milliseconds is acceptable to users.

### Where We Use Them
- Amazon DynamoDB, Apache Cassandra, Couchbase, Git version control, DNS record propagation, CDN caches.

---

## 81. Database Migrations

### What
Automated, version-controlled scripts that programmatically evolve a database schema over time (creating tables, altering column types, adding indexes) and apply them deterministically across local, staging, and production environments.

### Why
- Eliminates manual SQL execution in production, which is prone to human error, missed steps, and environment drift.
- Enables safe, automated schema updates within CI/CD pipelines, complete with forward (up) and rollback (down) scripts.

### Where We Use Them
- Migration frameworks: Flyway, Liquibase, Prisma Migrate, Alembic (Python/SQLAlchemy), Django Migrations, Rails ActiveRecord migrations.

---

## 82. Schema Versioning

### What
The practice of explicitly tracking the exact state and revision number of a database or serialization schema (e.g., Protobuf, Avro, JSON Schema) over time, ensuring backwards and forwards compatibility between services and storage engines.

### Why
- Deploying updated application code while old versions are still running causes runtime crashes if database columns or wire protocol fields are unexpectedly renamed or deleted (breaking change).
- Enforces evolutionary schema changes (expand-and-contract / parallel run pattern).

### Where We Use Them
- Confluent Schema Registry (Kafka Avro/Protobuf events).
- Zero-downtime database updates (e.g., Step 1: Add nullable column; Step 2: Deploy code writing to both; Step 3: Backfill; Step 4: Add NOT NULL constraint; Step 5: Remove old column).

## 84. Backups

### What
The scheduled copy and secure archival of database tables, WAL transaction logs, files, or persistent storage volumes to durable, isolated, off-site storage locations (e.g., AWS S3 Glacier, Google Cloud Coldline).

### Why
- The ultimate insurance policy against ransomware, accidental table drops (`DROP TABLE`), catastrophic datacenter fires, and data corruption.
- Satisfies legal, financial, and compliance mandates (SOC2, HIPAA, GDPR).

### Where We Use Them
- **Full Backups**: Periodic complete snapshots (e.g., weekly full dump).
- **Differential/Incremental Backups**: Capturing only changes made since the last backup.
- **Point-in-Time Recovery (PITR)**: Combining baseline snapshots with continuous WAL/binlog streaming to restore a database to any specific second before a corruption occurred.
- Tools: AWS RDS Automated Backups, pgBackRest, Percona XtraBackup.
